# Empyrean V2 — Database Schema Plan

## Overview

This doc covers all the database tables we need, why we need them, what goes in each column, and how they relate to each other. Think of it as the blueprint for Phase 2 of the TODO.

We'll use **PostgreSQL + TimescaleDB** (which is just PostgreSQL with a time-series extension). Most tables are regular PostgreSQL tables; only `sensor_readings` is a TimescaleDB hypertable because it stores massive amounts of time-stamped data.

---

## Table 1: `users` — who logs in

Both admins and regular users go here — the `role` column tells them apart.

| Column | Type | Why? |
|--------|------|------|
| `id` | `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | Unique ID (using IDENTITY not SERIAL — modern PostgreSQL practice) |
| `username` | `VARCHAR(50) UNIQUE NOT NULL` | Login name |
| `email` | `VARCHAR(255) UNIQUE NOT NULL` | For notifications / password resets |
| `password_hash` | `VARCHAR(255) NOT NULL` | bcrypt hash — never store raw passwords |
| `role` | `VARCHAR(20) NOT NULL DEFAULT 'user'` | `'admin'` or `'user'` — controls access |
| `notification_prefs` | `JSONB DEFAULT '{}'` | JSON for things like "email me on critical alerts" |
| `is_active` | `BOOLEAN DEFAULT TRUE` | Soft-disable an account without deleting it |
| `last_login_at` | `TIMESTAMPTZ` | When they last logged in — useful for audits |
| `created_at` | `TIMESTAMPTZ DEFAULT NOW()` | Account creation time |
| `updated_at` | `TIMESTAMPTZ DEFAULT NOW()` | Last profile update |

> **Change from v1:** Removed `health_condition` — too vague with no clear use case. We can add it later if needed.

**How admins vs regular users are created:**
- **Admin** — we manually insert a row via a seed script or directly in the DB. No public registration endpoint for admins.
- **User** — they register via `POST /api/v1/auth/register`. Gets `role = 'user'` automatically.

## Table 2: `refresh_tokens` — session management

**Why this exists:** JWTs are stateless — once issued, they can't be un-issued. The TODO requires:
- `POST /api/v1/auth/logout` — invalidate refresh token
- Refresh token rotation — secure handling

We need server-side storage to actually revoke tokens on logout and detect rotated/compromised tokens.

| Column | Type | Why? |
|--------|------|------|
| `id` | `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | Internal ID |
| `user_id` | `INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE` | Which user owns this token |
| `token_hash` | `VARCHAR(255) NOT NULL` | Hashed refresh token (never store raw tokens) |
| `expires_at` | `TIMESTAMPTZ NOT NULL` | Token expiry (matches JWT claim) |
| `created_at` | `TIMESTAMPTZ DEFAULT NOW()` | When it was issued |
| `revoked` | `BOOLEAN DEFAULT FALSE` | Set to TRUE on logout or rotation |

```sql
CREATE INDEX idx_refresh_tokens_user ON refresh_tokens(user_id);
CREATE INDEX idx_refresh_tokens_hash ON refresh_tokens(token_hash);
```

**How it works:**
- **Login** → create a row, return the token → `token_hash` is stored, raw token goes to client
- **Refresh** → verify old token, check hash matches & not revoked → revoke old row → create new row, return new token
- **Logout** → find row by hash → set `revoked = TRUE`

## Table 3: `nodes` — the sensor devices

Every ESP32 device out in the field gets a row here. When a device sends a reading, we look up its `node_id` to know *where* it is.

| Column | Type | Why? |
|--------|------|------|
| `node_id` | `VARCHAR(50) PRIMARY KEY` | Device ID, like `"ESP32-01"` or `"NODE-7a3f"` — comes from the device itself |
| `name` | `VARCHAR(100)` | Human-friendly name, e.g. "Downtown Sensor" |
| `location_name` | `VARCHAR(200)` | Text description of where it's placed |
| `lat` | `DOUBLE PRECISION` | Latitude for map display |
| `lon` | `DOUBLE PRECISION` | Longitude for map display |
| `firmware_version` | `VARCHAR(50)` | Which firmware the device runs — helpful for debugging |
| `reading_interval` | `INTEGER DEFAULT 30` | How often it sends readings (seconds) |
| `is_active` | `BOOLEAN DEFAULT TRUE` | Set to `FALSE` when a node goes offline or is retired |
| `registered_at` | `TIMESTAMPTZ DEFAULT NOW()` | When it was first added |
| `last_seen` | `TIMESTAMPTZ` | Last time we heard from it (updated by heartbeat/status messages) |

**Notes:**
- `lat`/`lon` are DOUBLE PRECISION, not PostGIS geography — the frontend handles GeoJSON mapping client-side.
- Using the device's own ID as the PK avoids extra joins. Device IDs are tied to hardware, so they don't change.

## Table 4: `sensor_readings` — the core data (TimescaleDB Hypertable)

This is the **big one**. Every 30 seconds, every node sends a reading. With 10 nodes that's ~28,800 rows/day; with 50 nodes ~144,000/day. A normal table would get slow — we use a TimescaleDB hypertable that auto-partitions by time.

### Raw sensor data (comes from the device)

| Column | Type | Range | Why? |
|--------|------|-------|------|
| `time` | `TIMESTAMPTZ NOT NULL` | — | When the reading was taken (hypertable partition column) |
| `node_id` | `VARCHAR(50) NOT NULL` | — | Which node sent it (FK to `nodes`) |
| `temperature` | `REAL` | 0–50 °C | Air temperature |
| `humidity` | `REAL` | 0–100 % | Relative humidity |
| `pressure` | `REAL` | 900–1100 hPa | Atmospheric pressure |
| `voc_ohm` | `REAL` | — | Raw VOC sensor resistance (BME680) |
| `mq135_ppm` | `REAL` | 0–1000+ | MQ135 sensor reading in PPM |
| `pm1` | `REAL` | 0–1000 µg/m³ | PM1.0 particulate matter |
| `pm25` | `REAL` | 0–500 µg/m³ | PM2.5 particulate matter **(most important for AQI)** |
| `pm10` | `REAL` | 0–1000 µg/m³ | PM10 particulate matter |
| `battery_v` | `REAL` | 0–5 V | Battery voltage — helps know if a node is dying |

> **Change from v1:** `REAL` instead of `DOUBLE PRECISION`. Sensor data doesn't need 15 decimal places of precision — REAL (4 bytes) vs DOUBLE PRECISION (8 bytes) saves ~50% storage on the largest table in the system. With millions of rows, this matters.

### Enriched data (added by the backend)

| Column | Type | Range | Why? |
|--------|------|-------|------|
| `fuzzy_score` | `REAL` | 0–100 | Output from Tsukamoto fuzzy inference engine |
| `aqi` | `SMALLINT` | 0–500+ | EPA-standard AQI from PM2.5/PM10 |
| `aqi_category` | `VARCHAR(40)` | — | "Good", "Moderate", "Unhealthy for Sensitive Groups", "Unhealthy", "Very Unhealthy", "Hazardous" |
| `is_anomaly` | `BOOLEAN DEFAULT FALSE` | — | Flagged by Z-score anomaly detection |

> **Change from v1:** `aqi` from `INTEGER` → `SMALLINT` (2 bytes instead of 4). AQI maxes out at 500+, comfortably within SMALLINT range (-32768 to 32767).

### Setup

```sql
-- Make it a hypertable partitioned by time
SELECT create_hypertable('sensor_readings', 'time',
    if_not_exists => TRUE,
    migrate_data => TRUE);

-- Speed up "all readings for node X in date range Y"
CREATE INDEX idx_readings_node_time
    ON sensor_readings (node_id, time DESC);

-- Also index time alone for global date-range queries
CREATE INDEX idx_readings_time
    ON sensor_readings (time DESC);
```

> **Note:** The migration uses `create_hypertable` with `if_not_exists => TRUE` (idempotent). Chunk interval, compression, and retention policies are not yet configured — they'll be added once the system is handling production data volumes.

> **Change from v1:** Added compression config (segmentby node_id for per-node decompression efficiency) and a `time DESC` index for global range queries.

> **Important:** Retention is managed by the TimescaleDB policy, NOT the `system_settings.data_retention_days` — if they diverge, data gets deleted inconsistently. The Celery worker will keep the policy in sync if the setting changes.

## Table 5: `hourly_agg` — pre-computed summaries (Continuous Aggregate — planned)

When the frontend asks "show average AQI for the last 30 days," scanning millions of raw rows would be slow. The final design uses a TimescaleDB continuous aggregate that auto-refreshes every hour.

> **Current status:** `hourly_agg` is a regular PostgreSQL table (not yet a continuous aggregate). It will be converted once the Celery aggregation logic (Phase 7) is implemented.

| Column | Type | Why? |
|--------|------|------|
| `bucket` | `TIMESTAMPTZ` | Start of the hour, e.g. `2026-07-27 14:00:00` |
| `node_id` | `VARCHAR(50)` | Which node |
| `avg_temperature` | `REAL` | Average temperature that hour |
| `avg_humidity` | `REAL` | Average humidity that hour |
| `avg_pm25` | `REAL` | Average PM2.5 that hour |
| `avg_pm10` | `REAL` | Average PM10 that hour |
| `max_aqi` | `SMALLINT` | Worst AQI that hour |
| `min_aqi` | `SMALLINT` | Best AQI that hour |
| `avg_aqi` | `REAL` | Average AQI that hour |
| `anomaly_count` | `INTEGER` | How many anomalous readings that hour |
| `reading_count` | `INTEGER` | Total readings in that hour |

> **Change from v1:** Added `anomaly_count` — useful for the dashboard to show "X anomalies detected in the last 24 hours" without scanning raw data.

> **Note:** The SQL below shows the *target* design. Currently `hourly_agg` is a regular table created via SQLAlchemy — the continuous aggregate conversion will happen in a future migration.

```sql
CREATE MATERIALIZED VIEW hourly_agg
WITH (timescaledb.continuous) AS
SELECT
    time_bucket('1 hour', time) AS bucket,
    node_id,
    AVG(temperature) AS avg_temperature,
    AVG(humidity) AS avg_humidity,
    AVG(pm25) AS avg_pm25,
    AVG(pm10) AS avg_pm10,
    MAX(aqi) AS max_aqi,
    MIN(aqi) AS min_aqi,
    AVG(aqi) AS avg_aqi,
    SUM(is_anomaly::int) AS anomaly_count,
    COUNT(*) AS reading_count
FROM sensor_readings
GROUP BY bucket, node_id;

SELECT add_continuous_aggregate_policy('hourly_agg',
    start_offset => INTERVAL '3 days',
    end_offset => INTERVAL '1 hour',
    schedule_interval => INTERVAL '1 hour');
```

## Table 6: `alerts` — threshold breach notifications

When AQI crosses a threshold, the system logs an alert. The frontend shows these on a map and as notifications.

| Column | Type | Why? |
|--------|------|------|
| `alert_id` | `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | Unique alert ID |
| `node_id` | `VARCHAR(50) NOT NULL REFERENCES nodes(node_id) ON DELETE CASCADE` | Which node triggered this |
| `parameter` | `VARCHAR(50) NOT NULL` | What crossed — `'pm25'`, `'aqi'`, `'temperature'`, etc. |
| `value` | `REAL NOT NULL` | The actual value that triggered it |
| `threshold` | `REAL NOT NULL` | Which threshold was crossed |
| `severity` | `VARCHAR(20) NOT NULL` | `'warning'` or `'critical'` |
| `message` | `TEXT` | Human-readable, e.g. "PM2.5 level 155 µg/m³ exceeds critical threshold 150" |
| `triggered_at` | `TIMESTAMPTZ DEFAULT NOW()` | When the alert fired |
| `acknowledged_at` | `TIMESTAMPTZ` | NULL = unacknowledged |
| `acknowledged_by` | `INTEGER REFERENCES users(id) ON DELETE SET NULL` | Which user acknowledged it (NULL = not yet) |

> **Change from v1:** 
> - `alert_id` from `UUID` → `INTEGER IDENTITY`. UUIDs are good for security, but alerts don't need to be unpredictable. INTEGER saves space and is faster for joins.
> - `value`/`threshold` from `DOUBLE PRECISION` → `REAL` — sensor data doesn't need double precision.
> - Added explicit FK constraints with ON DELETE behavior.

**Why this design:**
- Same table for both warning and critical alerts (filter by `severity`).
- `acknowledged_at IS NULL` = "still open."
- `triggered_at` lets you query "all alerts in the last 7 days."

## Table 7: `system_settings` — configurable knobs

Admins can tweak system behavior without touching code. Stored in the DB so changes persist across restarts.

| Column | Type | Why? |
|--------|------|------|
| `key` | `VARCHAR(100) PRIMARY KEY` | Setting name, e.g. `'aqi_warning_threshold'` |
| `value` | `TEXT NOT NULL` | Setting value, e.g. `'100'` (stored as text, cast when needed) |
| `description` | `VARCHAR(255)` | Human explanation of what this does |
| `updated_at` | `TIMESTAMPTZ DEFAULT NOW()` | When it was last changed |
| `updated_by` | `INTEGER REFERENCES users(id) ON DELETE SET NULL` | Which admin changed it |

### Default settings we'll seed

| Key | Default Value | Description |
|-----|--------------|-------------|
| `aqi_warning_threshold` | `100` | AQI value that triggers a warning alert |
| `aqi_critical_threshold` | `150` | AQI value that triggers a critical alert |
| `alerts_enabled` | `true` | Master toggle for alert generation |

> **Change from v1:** Removed `data_retention_days`. Retention is managed by the TimescaleDB policy directly. If we add it later, the Celery worker will sync the policy with the setting.

## How the tables connect (relationships)

```
users ─────< refresh_tokens    (one user can have many active sessions)
users ─────< alerts             (one user can acknowledge many alerts)
nodes ─────< sensor_readings    (one node sends many readings)
nodes ─────< alerts             (one node can trigger many alerts)
nodes ─────< hourly_agg         (one node has many hourly summaries)
users ─────< system_settings    (one admin can update many settings)
```

FK behavior:
- `refresh_tokens.user_id → users.id` — `ON DELETE CASCADE` (delete sessions when user is deleted)
- `alerts.node_id → nodes.node_id` — `ON DELETE CASCADE` (alerts are meaningless without the node)
- `alerts.acknowledged_by → users.id` — `ON DELETE SET NULL` (keep the alert even if user is deleted)
- `system_settings.updated_by → users.id` — `ON DELETE SET NULL` (keep the setting)

## Migration strategy

Two Alembic migrations:

**`eb88597519c9` — initial schema:**
1. Creates all 7 regular tables: `users`, `refresh_tokens`, `nodes`, `sensor_readings`, `hourly_agg`, `alerts`, `system_settings`
2. Creates indexes on `sensor_readings` and `refresh_tokens`
3. Foreign keys with cascade / set-null behaviour

**`b2bab23ab3c0` — TimescaleDB hypertable:**
1. Installs the TimescaleDB extension (`CREATE EXTENSION IF NOT EXISTS timescaledb`)
2. Converts `sensor_readings` to a hypertable partitioned on `time`

> **Note:** `hourly_agg` is currently a regular table. It will become a TimescaleDB continuous aggregate once the Celery aggregation logic is implemented. Compression and retention policies on the hypertable are also planned for later.
